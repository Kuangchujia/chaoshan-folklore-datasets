## 二、索引还是数据：三处谁拿什么

| 层 | 放什么 | 不放什么 |
|:---|:---|:---|
| **潮俗网** chaoshanwiki.com | 这件数据是什么、每条怎么核、不收什么。给人读。 | 不放整包文件 |
| **本仓** GitHub | 一件一行：覆盖范围、版本、许可、概念 DOI、站内页、原件出处。 | **不放任何数据文件** |
| **Zenodo** | 发布件本身：压缩包、校验和、`CITATION.cff`、`LICENSES.md`、`CHANGELOG`。 | 不做逐页说明 |

这里不留副本，就不存在「GitHub 版」与「Zenodo 版」对不上的问题。权威文件只有一套，在 Zenodo。若日后从这里直接供文件，这句话就不成立；目前不这样做。

两件顺带说清，因为这类索引多半坏在这两处：

- **数据不设第二个家。** 为了「方便」把同一个压缩包也传到本仓，就成了两个发布点，两套日期，最后是两份内容。
- **不悄悄替换。** 要改就出新的 Zenodo 版本；旧版的版本 DOI 一直可解析，去年写下的引用仍落在去年那件东西上。

## 四、为什么一律引「概念 DOI」

Zenodo 每一条记录有两个号：

| 号 | 性质 | 行为 |
|:---|:---|:---|
| **概念 DOI（concept DOI）** | 合集级 | **永久指向该合集的最新版本** |
| 版本 DOI（version DOI） | 记录级 | 固定在某一版，新版本发布后**不会跟着走** |

因此本索引一律只公布**概念 DOI**。日后出新版，同一串号照旧可用，不会停在旧版。

## 五、使用边界

- **只做转录，不做解释。** 记的是原件印的：项目类别、序号、项目名称、保护单位（第八批为申报地区）。不排名、不评价价值与真伪，不涉任何个人。
- **原件的缺陷照记，不代修。** 第七批序号 1—9 原件缺列，按表格行序补录，逐条在 `note` 写明；第八批序号 36、37 收尾括号原件作半角，照原文抄。
- **饮食标记与分组是作者加的。** 72 项标为饮食类，按工艺分 11 组；原件没有这套分类。
- **三份原件三种形态。** 第六批为 PDF 文本层，第七批为 `.doc` 复合文档，第八批为网页表格；合并单元格按上一行回填。
- **英文标题为工作定译**，不主张排他。
- 本系列不涉吉凶宜忌、择日与个体断语，一句都没有。
